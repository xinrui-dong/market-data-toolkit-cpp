# Market Data Toolkit usage guide

This C++17 program runs the following data-processing sequence:

~~~text
Read CSV -> validate dates and prices -> calculate returns and SMA -> write CSV
~~~

## Start with a hand-checkable example

The input file `data/sample_prices.csv` contains explicitly synthetic data:

| Date | Close price |
|---|---:|
| 2026-10-01 | 100 |
| 2026-10-02 | 110 |
| 2026-10-03 | 99 |
| 2026-10-04 | 108 |

Each simple price return is the current price divided by the previous price,
minus one:

- Second observation: `110 / 100 - 1 = 0.1`, a 10% increase.
- Third observation: `99 / 110 - 1 = -0.1`, a 10% decrease.
- Fourth observation: `108 / 99 - 1 = 1/11`, approximately a 9.09% increase.

The first observation has no previous price, so its return cell is empty. These
are changes between adjacent records. When dates have gaps, they are not daily
returns.

SMA is the arithmetic mean of the prices in a trailing window. For a window of
three observations:

- Third row: `(100 + 110 + 99) / 3 = 103`.
- Fourth row: `(110 + 99 + 108) / 3 = 317/3`, approximately `105.6667`.

The first two rows have fewer than three prices, so their SMA cells are empty.
Those empty cells are not zeros.

## Run the program

Install a C++17 compiler, CMake 3.24 or later, a build tool such as Make,
Doxygen, and Python 3.9 or later. Python checks the generated documentation using
only the standard library; no pip packages are needed. From the project root:

~~~sh
bash scripts/verify.sh
./build/bin/market_data --input data/sample_prices.csv --window 3 --output build/analysis.csv
~~~

The result is written to `build/analysis.csv`. A value such as
`0.10000000000000009` reflects rounding because `double` cannot represent every
decimal fraction exactly; it does not change the interpretation as approximately
10%. Output retains enough digits to recover the same `double` when read back.
Display the values as percentages if desired.

Omit `--output` to write the CSV to the terminal:

~~~sh
./build/bin/market_data --input data/sample_prices.csv --window 3 --algorithm naive
./build/bin/market_data --input data/sample_prices.csv --window 3 --algorithm rolling
~~~

Both algorithms use the same input and output definitions. The default is
`rolling`; `--help` lists the options. Test and benchmark dependencies are
included, so they do not need separate installation.

The complete verification sequence contains 31 CTest tests. Documentation uses
Doxygen's static menus to avoid alphabetic navigation links without targets in
short member lists generated by Doxygen 1.18.0. After generation, a checker
validates local HTML file links and page anchors and fails on missing targets.
Field and API-detail links remain available.

## Why compare two algorithms?

The naive algorithm sums each window again. The two example windows both
contain 110 and 99, so some work is repeated.

A mathematical rolling update keeps the current window sum. The first sum is
309; moving the window once gives:

~~~text
309 - 100 + 108 = 317
317 / 3 = 105.666666...
~~~

The departing price is removed and the arriving price is added. If `n` is the
number of prices, `w` the window length, and `q = n-w+1` the number of complete
windows, the naive implementation takes `O(n + q*w)` time, including validation.
Its returned vector uses `O(q)` storage and each window sum uses constant extra
space. Rolling aggregation takes `O(n)` total time.

The subtraction above is a real-number identity. With `double`, directly
subtracting a large departing price from a large sum can lose the small prices
that remain. The implementation therefore uses a **two-stack aggregate queue**
instead of subtracting departing prices from the total.

The back stack receives new prices and the front stack removes the oldest price.
When the front stack is empty, the back stack is transferred to it in reverse
order. Each stack level stores a compensated sum for the prefix ending there.
Removing a price pops one level; the remaining aggregate is already stored at
the next level. There is no subtraction of a large old price from a large total.

In the example, after 100 leaves, the front aggregate retains `110 + 99 = 209`.
The back aggregate receives 108. Combining them gives 317 and hence `317/3`.

Each price is inserted, transferred, and removed at most once. Total work is
`O(n)`, with `O(w)` queue workspace in addition to `O(q)` returned output
storage. A single transfer can process the whole window, so an individual step
is not guaranteed to be worst-case `O(1)`. Compensated summation and this queue
structure improve numerical behavior without making arbitrary `double` input
exact.

## Input rules and rejected data

The supported CSV has exactly two columns with the case-sensitive header
`date,close`. Dates must be valid Gregorian dates in `YYYY-MM-DD` format, in
years 0001 through 9999, and strictly increase. A close price must be a complete
decimal number, optionally in scientific notation, and be finite and strictly
positive. Surrounding spaces and tabs, CRLF line endings, and an optional
leading UTF-8 BOM are accepted.

The program rejects:

- Invalid dates, duplicate dates, or dates in descending order.
- Missing or incompletely parsed prices, trailing garbage, nonfinite prices,
  and prices that are not strictly positive.
- Missing or extra columns, quoted fields, and blank records. This is a
  restricted two-column format, not a general CSV parser.
- A window of zero, a negative or noninteger window, or a window larger than
  the number of observations.
- Extreme inputs whose intermediate calculations or results become nonfinite.
- An input file and output file that refer to the same file.

Diagnostics explain the reason; CSV errors usually include a line number. Exit
codes are 2 for invalid arguments, 1 for data, calculation, or file errors, and 0
for success. Integration tests check the exit code, diagnostic text, and empty
standard output on failure, so a crash or an unrelated error does not count as
the expected rejection.

With `--output`, input validation and calculation finish before a temporary
result is written on the destination filesystem. The destination is replaced
only after writing, flushing, and closing the temporary file all succeed. An
existing result is therefore preserved if a write fails partway through. A
directory or symbolic link is rejected as an output target. This handles
write and replacement failures during normal operation; it does not guarantee
durability after a power failure. Tests also inject a failure after partial
output and check the previous file contents and temporary-file cleanup.

Weekends, holidays, and date gaps are not automatically errors. Real input must
use one asset, currency, and consistent price basis. The program does not adjust
for corporate actions or automatically interpret price returns as total returns
including dividends.

## Interpret the benchmark results

Run `cmake --build build --target run_benchmarks`. Actual results are shown in
the terminal and saved to `build/benchmark.json`.

Each algorithm is measured at three input sizes and seven windows
`(1, 2, 3, 5, 10, 20, 100)`: 42 configurations in total. The default is three
repetitions per configuration, giving 126 raw measurements. Another 168 rows
contain aggregate statistics such as means and medians, for 294 JSON entries
in total. Aggregates are not additional measurements. The validator checks
every configuration name, three distinct repetition indices, and valid timings;
aggregate-only results or a missing repetition fail validation.

Input generation and CSV I/O are excluded from algorithm timing. Both algorithms
include input validation and result-vector allocation. Compare matching `n` and
`window` values rather than comparing different input sizes.

At `window=1`, both algorithms use a validation-and-copy path, so a large speedup
is not expected. Windows 2, 3, 5, and 10 compare the cost of adding a few prices
directly with the cost of maintaining the two-stack queue. Avoiding repeated
summation can become beneficial for larger windows. CPU load and hardware also
affect timing; complexity does not imply a fixed speedup.

In the local Release experiment on 2026-10-16, all three input sizes showed the
same pattern: naive was faster for windows 2, 3, and 5; rolling was faster for
windows 10, 20, and 100. Maintaining two stacks has overhead. Direct addition
costs less for small windows, while avoiding repeated summation becomes more
valuable as the window grows.

For 65,536 prices, the following times are medians of three CPU-time measurements,
in microseconds:

| Window | Naive SMA | Rolling SMA | Faster in this run |
|---:|---:|---:|---|
| 2 | 324.506 | 704.775 | Naive |
| 5 | 627.977 | 982.621 | Naive |
| 10 | 1337.400 | 1109.840 | Rolling |
| 100 | 27440.000 | 1264.000 | Rolling, approximately 21.71 times |

The sampled change in the winner lies between windows 5 and 10. Windows 6
through 9 were not measured, and this interval is not a fixed threshold for
other machines. The algorithm is still explicitly selected with `--algorithm`.
See the [benchmark results](benchmark-results.md) for all 21 paired workloads,
the raw JSON, and measurement conditions.
